The core question — "does this need a database?" — comes down to one fact: node positions, notes, and stroke paths are small text data that could theoretically live entirely inside the URL (zero backend), but actual recorded/uploaded **audio** is real binary payload (tens of KB to MB). That can't be crammed into a link — browsers and sharing apps (Slack, iMessage, etc.) truncate or choke well before that. So the moment audio needs to travel from your browser to someone else's via a link, *something* has to hold it at a stable address.

The good news: that something doesn't need to be a real database. It can be as dumb as a key-value blob store — one endpoint that takes the whole sketch (JSON for positions/notes/strokes + the audio files) and hands back a random ID, and one endpoint that returns that same bundle by ID. The "permission model" is just the ID being unguessable — no accounts, no ACLs, exactly the "anyone with the link" behavior you want. This is basically how Excalidraw's "share" link works (they also client-side encrypt so their server never sees content — a nice hardening step, but I'd skip it for v1 as unnecessary complexity).

For the collaboration model itself, I'd default to the simple version given your "keep it super simple" north star: **save/reload, not live sync** — opening the link always fetches the latest saved version; editing and it autosaves (or saves on some explicit action) overwrites that same ID. True live co-editing (seeing someone's cursor move in real time) needs websockets and a merge strategy — a lot more machinery for a sketchpad. [2026-11-05 18:59:15 UTC] CLAUDE

Here's the full lifecycle, then what it means for privacy/security.

## Where the audio actually lives, step by step

**Before you ever click Share:** audio only exists as an in-memory `Blob` in your browser, exposed via a `blob:` URL (`URL.createObjectURL`). It's never written to disk, never sent anywhere. Refresh the tab and it's gone — this hasn't changed since day one.

**The moment you click Share:** `serializeCanvas()` fetches each sound's local blob, base64-encodes it, and embeds it directly inside one JSON document alongside positions/notes/stroke paths (same schema we designed together). That JSON — audio included, as text — gets POSTed over HTTPS to `/api/sketch`.

**On the server:** the function writes that whole JSON document as a single object in your Vercel Blob store, at a path like `sketches/<id>.json`, marked `access: 'private'`. Vercel Blob itself is built on Amazon S3, in whichever region you picked when creating the store — so physically, the audio sits in an S3 bucket somewhere in that region, wrapped in Vercel's storage layer.

**Opening a shared link:** the browser calls `GET /api/sketch/<id>`. Your function (not the browser) authenticates to Blob storage and streams the content back. The browser never sees a raw storage URL — it only ever talks to your own `/api/sketch/*` routes. Once the JSON lands, the audio gets un-base64'd back into a fresh local blob: URL for playback, same as a live recording.

**Every autosave:** re-serializes the *entire* canvas — including every sound's audio again, not just what changed — and overwrites that same JSON blob. So editing one note re-uploads every recording currently on the canvas.

## What that means for privacy/security

- **"Private" access protects the storage layer, not your app.** Nobody can stumble on the raw S3-backed blob URL directly — good. But `/api/sketch/<id>` itself has **zero authentication**. Anyone who has (or guesses) the ~11-character ID can read *and overwrite* that sketch, audio included. That's the explicit design you asked for ("anyone with the link can edit"), but worth naming precisely: the *only* thing protecting a recording is the fact that its ID is unguessable — not encryption, not a login, nothing else.
- **It's "security by obscurity," the same model as an unlisted Google Doc or Dropbox link.** If a share link ever gets pasted somewhere semi-public — a Slack channel, a screenshot, browser history synced to a cloud account — anyone with access to that place can now reach the audio. That's an inherent property of link-based sharing, not a bug, but it's a real exposure path.
- **There's no expiry or deletion.** A shared sketch's audio sits in storage indefinitely once created — this was flagged as an accepted gap when we scoped the feature, but it's directly relevant to privacy: old recordings don't disappear on their own.
- **Transit is HTTPS end to end** (browser → function → Blob store, and back), so nothing's crossing the wire in plaintext.
- **Nothing gets logged in plaintext.** I just checked — the only `console` calls in the backend log the error object on failure, never the sketch/audio payload itself, so a crash doesn't leak recordings into Vercel's function logs.

Bottom line: the architecture is sound for what it's for — a quick, disposable, "nothing to configure" sketch-sharing link — but anyone who gets the link gets *everything*, forever, with no way to revoke it short of deleting the blob yourself. If you ever want to tighten this (link expiry, a delete-this-sketch action, or basic view-only vs. edit links), those are all reasonably small additions on top of what exists now — want to talk through any of them?

Is there any reseaon the maximum size is 4MB?

[2026-11-05 21:05:20 UTC] CLAUDE
--------------------------------
Yes — it's not arbitrary, it's a safety margin under a hard platform limit.

Vercel serverless functions cap the request/response body at **4.5MB**, across all plans (Hobby/Pro/Enterprise), for every function invocation. Since every save (`PUT /api/sketch/:id?objectId=...`) sends one object's full JSON — including its audio or image data, base64-encoded — through a single function call, that object has to fit under Vercel's 4.5MB ceiling or the platform itself rejects the request (a `413` error) before our own code even runs.

`MAX_OBJECT_BYTES` is set to 4MB specifically to leave headroom under that 4.5MB hard limit — enough margin for the surrounding JSON structure (field names, quotes, etc.) — so we catch an oversized object client-side with a friendly toast instead of letting it fail with an ugly platform error.

Worth knowing: base64 encoding inflates binary data by about 33%, so the *effective* ceiling on the original file is really closer to **~3MB of raw image/audio data**, not 4MB — which is why a several-MB phone photo trips it so easily while short audio clips almost never do.

If this becomes a real pain point, there's a known way to raise it (client uploads straight to Vercel Blob storage, bypassing the function body entirely) — but that's more moving parts than the current setup, so I'd only build it if the 4MB ceiling actually starts limiting you in practice rather than preemptively.

Now the walkthrough — treating "sketchbooks" as fully separate, agreed. Let's trace both navigation options through both device directions.

## Pan-only infinite canvas

Objects live at fixed coordinates in one continuous world; the viewport is just a window onto it, always at 1:1 — nothing ever visually shrinks or grows, you just see more or less of the world depending on how big your screen physically is.

**Big sketch → small device:** the sketch might span, say, 1800×1000 world-units. A phone's window only shows ~390×844 of that at once. You land somewhere (center of content? top-left? last position?) and see one slice — everything in it full-size and perfectly tappable, but you have no idea what else exists or where it is relative to you. You'd drag the empty canvas to explore, discovering the rest piece by piece, with no overview ever available.

**Small sketch → big device:** a sketch built on a phone, maybe 350×700, opens on a monitor with room to show 1920×1080. The whole thing just sits there, fully visible, with a lot of empty space around it. Complete non-issue.

So the pain is entirely one-directional — big-to-small is where you lose orientation.

One concrete implementation snag worth knowing before you lean this way: **"drag on empty canvas to pan" is the same gesture we already use for marquee-select.** Those two interactions would directly collide — we'd have to find a way to disambiguate them (a modifier key? two-finger drag only on touch, single-finger on desktop?), which isn't free.

## Scrollbars, canvas grows when you drag past the edge

The document has a size that starts somewhere and extends whenever something gets placed near its current edge (like a spreadsheet growing rows as you type). Scrollbars appear whenever the document is bigger than the viewport.

**Big sketch → small device:** document is still 1800×1000, phone viewport still ~390×844 — but now you *see* both scrollbars, with a small thumb on a long track, which is immediately legible: "this is much bigger than my screen, and I'm looking at the top-left corner of it." You scroll (and on a touch device, swipe-to-scroll is an extremely well-worn gesture — more discoverable than drag-to-pan, and it doesn't collide with marquee-select since it's a distinct scrollbar/scroll gesture, not a canvas-drag).

**Small sketch → big device:** same as pan — document fits entirely inside the bigger viewport, no scrollbars appear, nothing hidden. And there's a nice organic property here: if you then drag something toward the edge *on the big screen*, the document just grows to make room, regardless of which device is doing the growing.

So scrollbars solve the same core problem as pan, but add orientation (you always know there's more, and roughly how much) and dodge the gesture collision — at the cost of, well, having visible scrollbars, which is a real aesthetic choice (you called it "retro," which I think is fair — it reads more "old web app" than "infinite whiteboard").

## Fixed size, made more apparent

This one actually splits into two different behaviors depending on *what* "fixed" means, and I think that distinction matters a lot here:

**Variant A — fixed to whatever device started it** (today's actual behavior, just with a visible page boundary added): a subtle edge/shadow now shows you where the page stops.
- Big sketch → small device: you'd see a boundary confirming "yes, this page continues past your screen" — but with no scroll/pan paired in, you still can't *reach* the rest. This variant mainly converts silent confusion into honest, legible confusion. It doesn't fix reachability.
- Small sketch → big device: the small page sits fully visible with a clean boundary around it, like a Post-it on a big desk. Fully resolved, no issues.

**Variant B — one canonical size, same on every device** (closer to what "Illustrator page size" actually implies): the page dimensions are a property of the *document*, not whoever opened it.
- Small sketch → big device: same clean "Post-it on a desk" outcome as Variant A.
- Big sketch → small device: same reachability problem as Variant A — a boundary tells you there's more, but you can't get to it without scroll/pan.
- The wrinkle unique to B: if the canonical size is meaningfully bigger than a phone's own screen, you'd bump into that boundary *while creating something on your phone in the first place* — your own small sketch could have "page" edges you can't see the far side of, even on day one.

The honest summary: **fixed-and-visible, by itself, doesn't solve the problem you actually have** — it only makes the limitation legible instead of silent. It's really "option 5 plus a label," and only becomes a full answer to reachability if you pair it with scroll or pan, at which point you're really choosing between the two options above and using "make it visible" as a garnish on top.

Given that, the real fork is pan-no-zoom vs. scrollbars-with-growth — both solve reachability, the difference is orientation/overview (scrollbars win) versus aesthetic feel (pan feels more like a boundless sketchbook; scrollbars feel more like a windowed document) and that one gesture collision pan would force you to resolve. Audio correctness wouldn't change at all — playback is driven by `setTimeout`s scheduled off each sound's x-position, completely independent of scroll, so sounds already play correctly whether or not they're visible. The implications are all about *feel*, and there are a few real decisions hiding in what sounds like a simple tweak:

- **It fights manual scrolling.** If you're deliberately looking at something on the left while playback runs, auto-scroll would yank the view away to follow the playhead. And if you try to scroll during playback to glance ahead or behind, the next animation frame would just override you — there's no clean way to detect "the user meant to scroll" vs. "this is the programmatic follow" without added complexity (watching for scroll events and guessing).
- **Where does the playhead sit in the viewport?** Pinned at a fixed spot (e.g. always 25% from the left, revealing what's coming while keeping recent history visible) feels different from pinned at the left edge (pure reveal, nothing trailing) or centered (context both ways). No objectively right answer — it's a feel choice.
- **Smooth continuous scroll vs. something coarser.** Continuous tracking is basically free (one more line in the existing per-frame playhead update), but for a long, wide performance it means the view is slowly, continuously panning the whole time — which could be distracting if someone's trying to read a text annotation that's scrolling away from them mid-read.
- **Snap-to-start.** If you're scrolled somewhere else entirely when you hit play, should the view jump immediately to the start of the performance so you always see it begin? Probably yes, but that's itself a small jarring jump to decide on.
- **It only solves horizontal visibility.** Playback timing is x-only, so auto-scroll would only track left-right. If a sound is off-screen *vertically* when its turn comes, you still won't see it play — this doesn't fix that, and genuinely fixing it means panning toward each sound's actual position, not just a linear sweep.

None of that is hard, but none of it is a one-line change either — it's a handful of small judgment calls bundled into something that sounds like "just scroll the view." If you want, I'd lean toward the simplest version: snap to the start on play, then continuously scroll to keep the playhead at a fixed spot a bit left-of-center, and not bother handling "user scrolls mid-playback" specially for now — see how that feels before solving the harder half. Want me to build that, or talk through the viewport-position choice first?
